1 La arquitectura por módulos (las 4 capas + HTTP)

3 Las dos piezas transversales: lib/api.ts y lib/auth.ts

Ningún componente hace fetch “a pelo”: todo el HTTP pasa por un único cliente, y la sesión es reactiva gracias a useSyncExternalStore.

lib/api.ts — el único punto de salida a la API
API_URL
Base URL del backend desde .env.local (NEXT_PUBLIC_API_URL).
X-Usuario-Id
Header de autenticación que se agrega a TODOS los pedidos (se lee de localStorage).
ApiError
Error tipado: siempre sabemos el status HTTP y el mensaje amigable del backend.
401 → borrarSesion()
Si la sesión ya no sirve, se borra y el guard del layout redirige a /login.
const headers = { 'Content-Type': 'application/json' };
if (usuarioId !== null) headers['X-Usuario-Id'] = String(usuarioId);   // sesión

const r = await fetch(`${API_URL}/api${ruta}`, { method: metodo, headers, body: ... });

if (!r.ok) {
  const mensaje = datos?.mensaje ?? `Error HTTP ${r.status}`;
  if (r.status === 401 && ruta !== '/auth/login') borrarSesion();       // sesión inválida
  throw new ApiError(r.status, mensaje);                                // { mensaje } del backend
}
return datos;

export const api = { get, post, put, delete };   // ← TODA la app usa esta única interfaz
lib/auth.ts — sesión reactiva con useSyncExternalStore
iniciarSesion()
POST /auth/login → guarda { id, nombre, email, rol } en localStorage.
useSesion()
Hook reactivo: si cambia la sesión (login, logout o 401), todas las pantallas se actualizan solas.
tieneRol()
Oculta botones/menús según rol (UX). La autorización REAL la hace el backend.
snapshot servidor = null
Evita el “hydration mismatch” entre el HTML del server y el del navegador.
function suscribir(alCambiar) {
  window.addEventListener(CLAVE_SESION, alCambiar);  // cambios de ESTA pestaña (login/logout/401)
  window.addEventListener('storage', alCambiar);     // cambios de OTRAS pestañas
  return () => { /* removeEventListener… */ };
}

export function useSesion(): ISesionUsuario | null {
  return useSyncExternalStore(suscribir, leerSesion, sesionEnServidor);
}
// Por qué no useState+useEffect: localStorage es una fuente EXTERNA a React;
// esta API le dice a React cómo leerla y suscribirse, sin efectos ni bucles.
hooks/useXxxApi.ts — la carga inicial (el momento exacto del arranque) 
const [clientes, setClientes]   = useState<ICliente[]>([]);
const [cargando, setCargando]   = useState(autoCargar);   // ¡arranca en true!
const [error, setError]         = useState<string | null>(null);

const obtenerClientes = useCallback(() =>
  Promise.resolve()
    .then(() => { setCargando(true); setError(null); })
    .then(() => api.get<ICliente[]>('/clientes'))
    .then(lista => { setClientes(lista); setCargando(false); })   // → re-render
    .catch(e => { setError(e.message); setCargando(false); })
, []);

useEffect(() => { if (autoCargar) obtenerClientes(); }, [autoCargar, obtenerClientes]);
// ↑ el ÚNICO punto donde se dispara la primera carga: al montar el componente.

La forma .then() (y no async/await) cumple la regla ESLint react-hooks/set-state-in-effect, que prohíbe un setState síncrono directo en el cuerpo del effect.

4 Seguridad y rutas

Next.js separa las rutas públicas de las protegidas con route groups (las carpetas con paréntesis no aparecen en la URL) y protege el acceso con un guard en el layout.

🟢 Grupo público — (publico)/

sin login
  • / — landing
  • /tienda — catálogo de servicios y repuestos
  • /registro — alta de usuario (rol Recepción)
  • /login — inicio de sesión (fuera del grupo)

🔵 Grupo protegido — (app)/

requiere sesión
  • /dashboard, /clientes, /equipos
  • /ordenes (+ /nueva, /[id])
  • /usuarios, /servicios, /repuestos
  • /configuracion

Guard en app/(app)/layout.tsx — elegí un escenario:

1. Monta el layout Se ejecuta 'use client' + useSesion().
2. Lee la sesión obtenerSesion() → localStorage.
3a. Sin sesión Spinner “Verificando sesión…” → router.replace('/login').
3b. Con sesión Monta el shell: Sidebar + Header + contenido.

El spinner intermedio evita el “flash” de ver contenido protegido un instante antes de la redirección. replace() (y no push()) para que el botón “atrás” no vuelva a la ruta protegida.

const sesion = useSesion();                 // reactiva: null = sin sesión

useEffect(() => {
  if (obtenerSesion() === null) router.replace('/login');
}, [router, sesion]);

if (sesion === null) return <Spinner texto="Verificando sesión…" />;   // evita el flash
return <Shell><Sidebar /><Header /><main>{children}</main></Shell>;

Autorización en dos niveles (pregunta clásica de defensa)

NivelDónde viveQué hace
UX Frontend — tieneRol('admin') Oculta botones y menús que el usuario no podría usar. Es comodidad visual, no es seguridad.
Seguridad real Backend — [Authorize] + validación de rol por endpoint El backend valida en CADA request quién es el usuario (header X-Usuario-Id), si existe/está activo y si su rol permite la operación. Un id falsificado a mano no otorga permisos.

5 Preguntas de defensa — resumen

Respuestas cortas a las objeciones más frecuentes sobre el proyecto.

PreguntaRespuesta
¿Por qué solo React y Next.js, sin Redux ni React Query? El dominio son 6 módulos CRUD; Context + hooks cubre el caso sin el peso de librerías extra. Menos dependencias = menos riesgo de vulnerabilidades y de rotura por upgrades. Solo se agrega lucide-react (iconos).
¿Dónde está la seguridad si el guard es en el cliente? El guard es UX. La seguridad real está en el backend: header X-Usuario-Id validado por HeaderAuthenticationHandler + [Authorize] por endpoint.
¿Qué pasa si el backend cae? Nada queda en blanco: ErrorCarga muestra el mensaje y ofrece Reintentar (vuelve a ejecutar el GET).
¿Riesgo de guardar la sesión en localStorage? Es una decisión deliberada sin tokens: allí solo vive { id, nombre, email, rol } para la UI. El backend valida ese usuario en cada request; un id falsificado no sirve.
¿Escalabilidad? Cada módulo es autocontenido (página + Context + Vista + hook + interfaces). Agregar un módulo = replicar el patrón, sin tocar lo existente.
¿Rendimiento? Búsqueda filtrada en cliente (sin un request por tecla), páginas de listado como Server Components y el dashboard resuelve todo en un solo GET que arma el backend.
¿Testing y calidad? pnpm smoke prueba la capa de datos contra la API real (login, header, 401); pnpm lint y pnpm build (con typecheck) en cada entrega.
